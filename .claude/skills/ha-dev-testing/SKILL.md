# Tester dans le Home Assistant de dev

La section **Testing** de CLAUDE.md est la référence (démarrage / arrêt, tableaux de bord, entités de test, `dev/api.sh`). Ce skill ajoute ce qu'elle ne dit pas, appris à la dure.

## Avant tout

- `dev/ha.sh status` ; `dev/ha.sh start` s'il ne tourne pas (~7 s, y compris la première fois dans un worktree).
- `npm run build` après chaque modification sous `src/`, puis recharge la page. Pas de redémarrage de HA (seulement après un changement de `configuration.yaml`).
- **Chaque checkout a son propre HA, qui sert le bundle de ce checkout.** Le checkout principal est sur 8123. Dans un worktree git (ce qu'a un sous-agent lancé avec `isolation: "worktree"`), lance `dev/ha.sh start` **dans le worktree** : il prend le premier port libre à partir de 8124 (`dev/.ha-port`), initialise une instance neuve (token propre, `/plooum-edit`, zones) et lie le `.venv` et `node_modules` du checkout principal pour que `npm run build` et `dev/.venv/bin/python dev/ui_test.py ...` marchent tels quels. Ne teste jamais sur le port d'un autre checkout (tu testerais son code).
- `dev/ha.sh status` affiche ton URL ; `dev/ha.sh list` liste toutes les instances qui tournent (port, pid, checkout). `dev/shot.py`, `dev/ui_test.py`, `dev/api.sh`, `dev/bootstrap.py` choisissent ton instance tout seuls (`--url` / `HA_URL` forcent autre chose). **Lance-les depuis ton propre checkout.** Plusieurs instances à la fois se ralentissent mutuellement (une suite a pris 28 s seule, 60 s avec trois en même temps) : ça va, ne baisse pas les délais.
- **Quand tu as fini, `dev/ha.sh stop` dans ton worktree** (le pilote supprime le worktree après la fusion ; une instance laissée en route garde ~270 Mo).

## Le tableau des agents

Le tableau est `plooum/agent-board`, installé dans `~/.local/opt/agent-board` (`AGENT_BOARD_HOME`), facultatif (rien n'échoue sans lui) : une page générique (par défaut http://127.0.0.1:8120, voir son README) où l'utilisateur suit les agents, **y compris une vue en direct, en lecture seule, du navigateur de chaque agent**. `dev/ha.sh start` y enregistre ton checkout (worktrees de sous-agents seulement, pas le checkout principal). `dev/ui_test.py` rapporte tout seul ses exécutions et ses tests, résolus à partir de ton port HA, **diffuse son Chrome sans interface** vers le tableau (un screencast, `board_stream.py` ; les exécutions portent le projet, le chemin du checkout principal) et poste une capture par test terminé ; `dev/shot.py` diffuse aussi ses images en direct. Rien à faire. Si le tableau ne tourne pas, rien ne se passe et rien n'est plus lent. `--board <url>` sur l'un ou l'autre script poste vers un autre tableau. Le tableau garde chaque exécution dans son historique de tests (30 jours) : une suite jetable (un JSON de brouillon pour déboguer une étape) se lance avec `--board ''`, pour qu'elle n'y atterrisse pas ; les suites de ta PR se lancent avec le tableau par défaut.

## Quel navigateur

- **Les sous-agents n'utilisent jamais le panneau navigateur intégré** (`mcp__Claude_Browser__*` ; utilisateur, 2026-10-12) : il ne peut pas être répliqué sur le tableau, et l'utilisateur regarde là-bas ton Chrome sans interface (http://127.0.0.1:8120). Le panneau est pour le pilote et l'utilisateur (`runner.html`, plus bas).
- Tout ce que tu fais dans un navigateur passe par Chrome sans interface via Playwright, qui diffuse vers le tableau :
  - `dev/shot.py` pour une page ou une carte, et pour les vérifications à la main : `--js` évalue une expression après le chargement, `-e` recadre sur un élément (code de sortie 1 en cas d'erreurs de console) ;
  - `dev/ui_test.py` pour tout le reste : tous les cas de test d'une fonctionnalité en une **suite**, avec des assertions (voir plus bas).
- Disposition téléphone : `--width 420 --height 900`. HA 2026.10 **empile alors l'aperçu de la boîte de dialogue de l'éditeur sous l'éditeur** (rendu, ~2900 px plus bas, hors de vue), il ne le cache pas : « rendu avec une taille non nulle » ne dit pas si la boîte est étroite. Vérifie plutôt si l'aperçu est *à côté* de l'éditeur (pas de chevauchement horizontal).

## Suites : sans interface, suivies sur le tableau

Lance chaque suite avec `dev/.venv/bin/python dev/ui_test.py dev/tests/<name>.json [--only <substring>]` ; fais les vérifications à la main (clics, éditeur, états) avec `dev/shot.py ... --js`, ou comme une suite d'un seul test. L'utilisateur suit le flux sur le tableau, toi tu lis la sortie PASS / FAIL. Exactement les mêmes étapes tournent dans le panneau par `runner.html?suite=<name>[&only=<substring>][&pause=<ms>]` (une iframe de même origine par test, réduite pour le panneau ; lis `window.uiResult`), mais **cette page est pour le pilote et l'utilisateur, pas pour les sous-agents**. Les étapes `shot` y sont ignorées. La langue de l'utilisateur de dev est l'anglais (réglée par `dev/bootstrap.py`, relance-le sur une instance plus ancienne). `dev/runner.html`, `dev/ui_runner.js`, `dev/ui_helpers.js` et les suites sont servis par l'intégration `plooum_dev` (redémarre HA une fois après avoir mis à jour un checkout antérieur à cette fonctionnalité).

## Tester une fonctionnalité avec une suite, pas avec une exécution par vérification

**Règle : écris les cas de test de la fonctionnalité sous forme de suite dans `dev/tests/<feature>.json` et lance-la en une commande ; ne regarde des captures d'écran que pour celles dont le rapport a besoin.** Une exécution qui ouvre l'éditeur coûte ~3 s (un navigateur pour toute la suite, pas d'attentes fixes), mais chaque appel d'outil est un aller-retour avec le modèle : une exécution par vérification, ou lire des captures pour voir un résultat, est ce qui rend les tests lents.

```bash
dev/.venv/bin/python dev/ui_test.py dev/tests/floorplan-setup-view.json [--only <name substring>] [--out dev/shots] [--verbose]
```

Sortie : une ligne `PASS  1.8s  <name>` / `FAIL` par test, puis pour chaque échec l'étape en échec, son message, la valeur et les erreurs de console de ce test ; le temps total ; code de sortie 1 en cas de test échoué ou d'erreur de console. Un test qui échoue n'arrête pas la suite. La docstring de [dev/ui_test.py](../../../dev/ui_test.py) donne le format ; [dev/tests/floorplan-setup-view.json](../../../dev/tests/floorplan-setup-view.json) est l'exemple à copier.

- Une suite : `path`, `viewport`, `tests[]` ; un test : `name`, `path` / `viewport` facultatifs, `steps[]`. Chaque test démarre sur un **chargement de page neuf** (même navigateur), donc l'état d'une boîte de dialogue ne fuit jamais d'un test à l'autre.
- Étapes : `{"js": "<corps async>"}` (valeur affichée avec `"print": true` ou `--verbose`), `{"assert": "<expression ou corps async qui renvoie une valeur>", "msg": "...", "show": "<expression affichée en cas d'échec>"}`, `{"shot": "x.png", "el": "<expression qui renvoie un élément>"}`, `{"wait": ms}` (une vraie animation seulement : préfère `waitFor` / `fp.waitIdle`).
- `"finally": [steps]` sur un test : des étapes qui tournent toujours après `steps`, même après un échec ; mets-y les restaurations d'état.
- `"same_page": true` sur un test : il tourne dans la page du test précédent sans recharger (économise le chargement de page et l'éditeur à froid), seulement si ce test a tourné dans la même page du lanceur, a réussi et a le même chemin et la même taille d'écran ; sinon la page se charge comme d'habitude. Donne-lui un `finally` qui laisse la page propre (`await closeDialogIfOpen();`, restaure ce que le test a changé).
- `ui_test.py` lance chaque groupe de tests `same_page` consécutifs (même taille d'écran) dans une seule page du lanceur (`runner.html?index=3,4,5`, une liste séparée par des virgules) ; `--only` sur un test `same_page` seul charge simplement la page. `--verbose` affiche le temps de chargement ou de réutilisation de page de chaque test.
- Les étapes voient les helpers par leur simple nom, plus `T` et `S` (= `T.s`, un objet brouillon gardé pendant toute la vie de la page : **mets dans `S` ce dont l'étape suivante a besoin**, les variables locales ne traversent pas les étapes). `JSON` n'a pas de commentaires, mais le lanceur saute les lignes qui commencent par `//`.
- Les helpers vivent dans [dev/ui_helpers.js](../../../dev/ui_helpers.js) (injectés une fois par page sous `window.T`) : `deep`, `sleep`, `waitFor(fn, timeout, what)`, `pointerDrag`, `tap`, `openEditor(stackIndex)`, `editor()`, `previewCard(title)`, `dashboardCards()`, `cancelDialog()`, et pour le floorplan `fp.selectEntity`, `fp.dropCorner`, `fp.dropCornerInPlace`, `fp.dragPicture`, `fp.orbitDrag`, `fp.waitIdle`, `fp.setupBadge`, `fp.setupState`, `fp.snapshot` / `fp.unchanged`. Pour n'importe quelle carte, `T.card.rendered(tag, count)` (cartes rendues, aucune `hui-error-card` ; passe le nombre **réel** de cartes de la vue : le tableau de bord construit les cartes paresseusement, donc avec un nombre plus bas il rend la main avant que les autres existent et une vérification ultérieure devient instable sur une instance à froid), `T.card.all`, `T.hass()`, `T.card.call(domain, service, data)`, `T.card.waitState(entity, predicate)` et `T.card.editorRenders(card)` (construit l'éditeur sans la boîte de dialogue et échoue sous 3 éléments dans son shadow root : un éditeur qui n'est qu'un `ha-form` seul a besoin d'un autre élément, par exemple une ligne d'aide ; il est ajouté à côté de la carte, pas à `body`, car le contexte de HA, `localize` compris, n'atteint que les éléments à l'intérieur de l'app). [dev/tests/cards-smoke.json](../../../dev/tests/cards-smoke.json) est l'exemple d'une suite qui les utilise. Le shadow root d'une carte peut ne contenir qu'un seul enfant (`ha-card` ; ses styles sont adoptés, pas des éléments `<style>`) : teste le contenu rendu avec `children.length > 0`. Il en manque un ? Ajoute-le là (une carte d'un autre genre a son propre espace de noms), pas en JS copié-collé dans chaque suite.
- Attends des conditions, jamais du temps : `await waitFor(() => <predicate>, 8000, 'what')`. Récupère de nouveau un élément (`previewCard(...)`) après tout ce qui peut le reconstruire : HA recrée la carte de l'aperçu sur `config-changed`.
- Écris l'assertion qui échouerait sans la fonctionnalité (par exemple `_orbit === null` avant, défini après), et une sur les cartes qui ne doivent pas changer.

## La boîte de dialogue de l'éditeur (ce sur quoi s'appuient les helpers, pour quand il t'en faut plus)

- Les éditeurs de carte ne s'ouvrent que sur le tableau de bord en mode stockage : `/plooum-edit/<view>?edit=1`. Le libellé du bouton de modification est `Edit` (la langue de l'utilisateur de dev est l'anglais, réglée par `dev/bootstrap.py`).
- `/plooum-edit/floorplan` est une vue panneau qui contient **une pile verticale** : la boîte de dialogue montre l'éditeur de pile avec les onglets 1..6. Choisis une carte : `stack = hui-stack-card-editor; stack._selectedCard = i; stack.requestUpdate()` (`openEditor(i)` le fait). La carte 3 (indice 2) est « Home in 3D », la carte 1 (indice 0) « Home » (2D).
- L'aperçu de la boîte de dialogue montre **toute la pile** : la carte que tu édites peut être hors écran (`scrollIntoView()`).
- Dans une page où la boîte de dialogue est ouverte, les cartes du tableau de bord derrière elle existent aussi, avec la même configuration. `card.preview` ne permet pas de les distinguer (vrai pour les deux en mode édition) : cherche à partir du shadow root de `hui-dialog-edit-card` (`previewCard`, `dashboardCards`). Le tableau de bord rend certaines cartes paresseusement : ne compare que celles dont tu as pris un instantané.
- Shadow DOM : `querySelector` ne traverse pas les shadow roots, ni un sélecteur descendant dans `deep()`. Parcours les racines, ou remonte l'arbre composé avec `node.parentNode || node.host`.
- Agis sur les composants lit par leurs propriétés réactives, par exemple l'éditeur floorplan : `ed._selection = { kind: 'entity', index }`, `ed._cameraAdvanced = true`, puis `await ed.updateComplete`.
- Pour simuler une action de l'utilisateur qui émet `config-changed`, appelle le vrai gestionnaire ou déclenche le vrai événement DOM (comme le fait `fp.dropCorner`) plutôt que de fixer la configuration.
- `<input type="color">` natif : fixe `.value` et déclenche un événement `input`.
- `PointerEvent` synthétiques (faits par `pointerDrag`) : `setPointerCapture` lève une exception sur un `pointerId` inventé (neutralisé), `pointerdown` va à la cible, `pointermove` / `pointerup` à l'élément qui porte les gestionnaires, avec `bubbles`, `composed`, `button: 0`, `isPrimary`. L'éditeur floorplan ignore les déplacements de moins de 4 px (un tapotement) : `fp.dropCornerInPlace` sort puis revient. `T.pointerDrag(el, null, to)` part du centre de `el` : passe un `from` explicite quand la cible du pointerdown est un petit rectangle de détection. L'étendue de la grille de l'éditeur floorplan (`ed._ext`) grandit après un tracé : recalcule les coordonnées client à partir de `_ext` en direct avant chaque glissement.
- Une étape `shot` avec `el` réglé sur `hui-dialog-edit-card` échoue (découpe de taille nulle, `display: contents`) : omets `el` pour une capture de page entière.
- `hui-dialog-edit-card` reste dans le DOM après **Cancel** : sa présence ne dit pas que la boîte est ouverte (`T.editor()` le dit). Pour la carte floorplan, `fp.setupState().size` vaut 0 une fois toutes les boîtes de dialogue d'éditeur fermées.
- `wait_for_function` n'attend pas une promesse : la vérification de disponibilité du lanceur est synchrone (connecté, chaque `hui-card` a construit sa carte, les cartes sont rendues).

## Vérifier

- Erreurs de console : code de sortie de `dev/shot.py` / `dev/ui_test.py`. Les deux ne rapportent que les erreurs, pas les lignes `console.info` / `log` (par exemple la bannière de version d'une carte) : affiche-les avec `dev/shot.py --console <substring>` (répétable, n'importe quel type de console, insensible à la casse). Le tampon de console du panneau intégré garde d'anciens messages (échecs de websocket lors d'un redémarrage de HA) : ne t'y fie pas pour une vérification propre.
- Une carte dont `setConfig` échoue est une `hui-error-card` invisible hors du mode édition : cherche-la dans le DOM.
- Actions : vérifie l'entité ou le compteur sous-jacent avec `dev/api.sh GET states/<entity>`.
- `dev/shot.py -e` prend un sélecteur Playwright, donc `-e ".view3d >> nth=1"` recadre sur la deuxième vue 3D ; `--js` s'exécute une fois cet élément présent (règle-y la configuration d'une carte ou `_orbit`).
- Donne les chemins des captures dans ton rapport. Garde-les dans `dev/shots/` (gitignored), ne les commite jamais.
